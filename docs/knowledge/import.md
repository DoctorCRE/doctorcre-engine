## Copy and reconcile

1. Enumerate source versions under stable keys such as store, source ID, and source revision. Partition inventory keys into copied, already represented, archived, or unresolved. A split names all destination keys. A duplicate names the retained row. Preserve each original key and source locator, including where several sources support one fact. Keep reconciliation counts and exceptions with the private input. Public checks use made-up fixtures.
2. Resolve traits, source links and lender programs against copied IDs. Keep missing scope, ambiguous ownership, unmatched terms and unsupported typed values unresolved with their original source keys and reasons. Never widen a scope to get a row copied. Preserve unknown source dates as unknown.
3. Copy business history as reference revisions with original attribution and dates where known. Use the existing copy attribution mapping, or `old_system` when only the job can be named. Import effective candidates as drafts for partner review. A lesson stays reference. A source's old approval can be cited as evidence. Activation in the new database requires a recorded partner approval using the [revision rules](tables.md#approval-and-history).
4. Use deterministic import keys, including a stable child key when a source is split. Rerun against the same input and compare the per-kind counts, revision IDs, attribution and live outputs. Preserve any partner edits that happened after the copy. The copy refuses a reused key with different source content and leaves past revisions intact.
5. Before switching consumers, reconcile every eligible source key and every existing checklist or timing key. A shared approval must come from a partner. Private rows with unknown ownership stay unresolved and do not enter a shared review. Compare old and new checklists on the same made-up deals before enabling the new projection. Preserve old data in its source archive.
