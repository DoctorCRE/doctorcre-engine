## Q1 Standing grant scope

Which actions require approval and what counts as the same kind? Options are an action kind alone or a kind with the target and capability limits shown in the request. Recommend scoped grants with one decision for repeat use within scope. For a paused request, either resume an exact live action or store the grant and restart from current facts if the attempt expired. Recommend the latter for expired attempts, with no automatic dispatch from a late decision. A CLI with a native approval interface could supply pre-dispatch requests if it can leave the decision to Doc. Otherwise route the applicable actions through Doc's tools. Prove coverage before enabling an unrestricted driver for actions Doc must control.

## Q2 Unattended mail

Does switching off base restrictions apply to unattended mail? Options are keeping mail tool-less, or letting mail request authorized tools through Doc. Recommend keeping the existing owner-controlled `allowMailTools` switch off and leaving jobs queued when the runner cannot isolate them. These jobs read outside email and run without a partner in the chat.

## Q3 Business confirmations

Should a standing action grant authorize future DoctorCRE saves or sends by itself? Options are preserving confirmation for each concrete transaction or defining explicit exceptions for selected actions. Recommend preserving the current app confirmation and send rules. A standing grant authorizes the kind of tool action. The save or send confirmation binds the exact record, text, recipients and version for one transaction.

## Q4 Loading and evidence

Should open-ended chats select a playbook by the wording of the question or only use playbooks launched from known app actions and explicit requests? Recommend selection from explicit context or requests for the first two playbooks. For deal activity outside the current projection, either show what is available or extend the engine projection for an approved scenario. Recommend adding fields only when a trace case identifies a missing fact. Reuse decision 220's structured numeric checks where a visual is used. Decide which structured values should also appear outside visual blocks.

## Q5 Filing without a review

When a named email has no pending filing review, should Doc link to its current activity or offer a new filing action? Recommend showing the available source and its state first. Define a separate door and approval if creating a filing review is needed.

## Q6 Later tools and sessions

Should the next expansion start with the existing vendor and Calendar doors or the first record-button session? Recommend picking the next workflow after exact-email filing. Calendar booking, chat attachments and new-email sending need approved contracts. Decide who sees another partner's session status and what ties the session to the record. Recommend sharing the approved result on the record while keeping the conversation private. [Doc sessions](../new-database.md#doc-skill-sessions)

## Q7 Preference values and team edits

Should both partners edit team defaults directly or should one partner own those edits? Recommend letting both edit the shared row with the ordinary write proofs. For draft length and comparison format, choose named values or bounded custom values. Recommend starting with named values and leaving rows unset until a partner chooses. The exact names and the playbook baseline need approval before building the preference keys.
