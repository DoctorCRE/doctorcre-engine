# Set up Doc for a partner

The shared template is the Doc instructions, tool definitions, made-up test fixtures, drivers, installer and LaunchAgent in the engine checkout. In chat, the Mac and backup read approved playbooks and guidance through the engine tools. Setup copies no knowledge to the Mac. [Playbook reads](playbooks.md#read-approved-playbooks-and-guidance) Each partner supplies their account, Mac login, supported CLI installations and personal plan sign-ins. Each link owns one revocable engine credential. Each partner has their own model choices, personal preferences and standing grants. Team preferences are shared through the engine. [Decision 195 and decision 217](../decisions.md) · [Memory](memory.md)

## Use the same command on each Mac

1. Start on Joe's Studio in Joe's normal login. Prepare the engine checkout with Node 26 and `npm ci`. Install supported CLIs and sign in through each desired CLI with the partner's own plan and usage credits off. The business approves automated use under each provider's terms before enabling the driver.
2. In the prepared checkout run `bash scripts/install-doc-link.sh "$DOC_ENGINE_ORIGIN"` with the intended HTTPS origin. The installer checks installed CLI support and sign-in, and verifies the existing link for that same origin. On a fresh Mac, issue a credential in Settings and enter it at the hidden prompt. The engine shows it once and stores its hash. Replacing it revokes the previous credential. Avoid printing it or putting it in shell arguments.
3. Setup writes owner-only `~/Library/Application Support/DoctorCRE Doc/link.json` at mode `0600`. It records the engine origin, credential, and supported backend paths and starts or reloads the existing LaunchAgent. The runner reports each detected supported provider and its readiness. Rerun this command to register another CLI or update local paths. Reuse the same verified credential when the origin and link match. A rejected link needs a fresh credential. A CLI's plan and sign-in stay in that CLI.
4. Open Ask Doc and check the available providers. On a Codex-only Mac with no saved choice, select and save Codex as first choice before sending the first question. Setup registers Codex without asking for a Claude Code install or sign-in. Send a made-up deal question and open its exact source. Repeat under Dell's login on Dell's Mac, using Dell's link and plan. Provision a future member's DoctorCRE account and record access first, then use the same steps with that member's Mac, account and plans. [Connect a Mac](../new-database.md#connect-a-mac-to-doc)

## Ask Doc picker

After [#1508](https://github.com/DoctorCRE/doctorcre-engine/pull/1508), the link probes the real CLI in chat mode and in mail mode. Each reports ready or unavailable with a plain reason. The engine uses the relevant result for claims and backup. The picker adds a catalog with model and effort choices, and uses chat readiness to show available chat providers.

Save a first provider and an optional distinct second provider in Ask Doc. Each can use a reported model and effort or the CLI defaults. With no saved row, the first choice is Claude Code. A Codex-only Mac prompts the partner to save Codex before the first question. A new choice applies to the next claim. The engine credits the provider that answers. Mail uses the configured Mac backend. [Decision 218](../decisions.md) · [#1507](https://github.com/DoctorCRE/doctorcre-engine/issues/1507) · [F5](flows.md#f5-mac-waiting-and-provider-fallback)

For chat, configure the base CLI without its own restrictions or permission prompts once the driver can pass approval decisions through Doc before dispatch. Set up an approved driver the same way for a later provider. Verify its passive status, model selection, and Doc approval path, as well as tool-less mail while that rule applies.
