# Set up Doc for a partner

The shared template is the role, playbooks, tool definitions, made-up examples, driver definitions, installer and LaunchAgent in the engine checkout. Each partner supplies their account, Mac login, supported CLI installations and personal plan sign-ins. Each link owns one revocable engine credential. Each partner has their own model choices, personal preferences and standing grants. Team preferences are shared through the engine. [Decision 195 and decision 217](../decisions.md) · [Memory](memory.md)

## Use the same command on each Mac

1. Start on Joe's Studio in Joe's normal login. Prepare the engine checkout with Node 26 and `npm ci`. Install supported CLIs and sign in through each desired CLI with the partner's own plan and usage credits off. The business approves automated use under each provider's terms before enabling the driver.
2. In the prepared checkout run `bash scripts/install-doc-link.sh "$DOC_ENGINE_ORIGIN"` with the intended HTTPS origin. The installer checks installed CLI support and sign-in, and verifies the existing link for that same origin. On a fresh Mac, issue a credential in Settings and enter it at the hidden prompt. The engine shows it once and stores its hash. Replacing it revokes the previous credential. Avoid printing it or putting it in shell arguments.
3. Setup writes owner-only `~/Library/Application Support/DoctorCRE Doc/link.json` at mode `0600`. It records the engine origin, credential, and supported backend paths and starts or reloads the existing LaunchAgent. The runner reports each detected supported provider and its readiness. Rerun this command to register another CLI or update local paths. Reuse the same verified credential when the origin and link match. A rejected link needs a fresh credential. A CLI's plan and sign-in stay in that CLI.
4. Open Ask Doc, check readiness, send a made-up deal question, and open its exact source. Repeat under Dell's login on Dell's Mac, using Dell's link and plan. Provision a future member's DoctorCRE account and record access first, then use the same steps with that member's Mac, account and plans. [Connect a Mac](../new-database.md#connect-a-mac-to-doc)

## Ask Doc picker

The existing link reports provider, `ready`, `signed_out` or `plan_limited`, a reset when supplied, and model IDs, labels and allowed efforts. The engine replaces that partner's reported list on each full report. A replacement credential clears the list and preserves model choices. Older readiness-only reports mean Claude. Ask Doc lists ready choices for that partner and explains sign-out, limits or Mac offline from link status.

The partner saves a first provider and optional distinct second provider, each with optional model and effort. The engine accepts only reported providers and listed models and efforts. Null model and effort use the CLI defaults. With no saved row, use Claude Code with its defaults. Changing a choice applies to the next claim, including in existing chats. The picker uses the same link without issuing another code. If a previously selected model or effort disappears, use that CLI's default. [Decision 218](../decisions.md) · [Model choice](../new-database.md#model-choice) · [#1507](https://github.com/DoctorCRE/doctorcre-engine/issues/1507)

The engine includes both choices on a chat claim. Combined readiness is ready when either choice is ready. Otherwise it is plan-limited with the earliest reported reset among limited choices, or signed-out when neither is limited. The ready second choice can run when the first reports signed-out or plan-limited. The engine saves the provider that answered. Existing `mac` answers migrate to `claude` under the documented plan. History is provider-independent. Mail jobs use the configured Mac backend and F7 policy. Backup follows F8 eligibility and attribution. [F5](flows.md#f5-mac-waiting-and-provider-fallback) · [F7](flows.md#f7-unattended-mail) · [F8](flows.md#f8-prepaid-backup)

For chat, configure the base CLI without its own restrictions or permission prompts once the driver can pass approval decisions through Doc before dispatch. Set up an approved driver the same way for a later provider. Verify its passive status, model selection, and Doc approval path, as well as tool-less mail while that rule applies.
